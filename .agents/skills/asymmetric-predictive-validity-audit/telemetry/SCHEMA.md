# Evaluation telemetry schema

Schema: `apva.eval.telemetry.v1`.

This telemetry is generated by the packaged evaluation harness, not by the skill during ordinary audits. That distinction is mandatory because a skill cannot observe a routing miss on a turn where Codex never injected it.

## Evidence classes

- **Routing evidence:** native Codex OpenTelemetry metric `codex.skill.injected`. The harness treats absence of the target metric as a non-activation only when the OTLP metrics stream is otherwise live. If no Codex metrics arrive, routing is `unknown`, never a fabricated miss.
- **Task evidence:** the produced `report.md`, the deterministic `validate_audit_report.py` result, and case-specific hidden rubric patterns from `evals/corpus.json`.
- **Recovery evidence:** the same artifact checks applied to deliberately adverse cases. A failed recovery is recorded separately from an initial task failure.
- **Cost evidence:** `codex exec --json` token usage and completed item types plus harness wall time. Raw prompts are not copied into telemetry events; case IDs bind back to the versioned corpus.

## Event names

- `eval.run.started`, `eval.run.finished`
- `eval.case.started`, `eval.case.finished`
- `routing.observed`, `routing.miss`, `routing.false_activation`
- `task.result`, `task.failure`
- `recovery.result`, `recovery.failure`
- `cost.observed`
- `evidence.unavailable`, `evidence.invalid`

Every case result is also stored as `result.json` beside its trace so the run can be rescored later without rerunning Codex.

## Experimental conditions

Routing cases exercise implicit selection. Task/recovery `skill` cases prepend an explicit `$asymmetric-predictive-validity-audit` treatment so task quality is not confounded with routing recall. Baseline cases do not stage the target skill and use the same neutral task prompt; native target injection in a baseline is `baseline_contamination` and invalidates that result.
