## Authoritative condition semantics (gate for item 3: CLEARED)
Sources obtained and read locally (text extracted from the PDFs):
- **CTA CTS Pillar Multicast Output Binary Specification v2.11b, 29 Jan 2026** (`ctaplan.com/publicdocs/ctaplan/CTS_Pillar_Output_Specification.pdf`), "Sale Condition" field description: per-code "Consolidated Last" column plus Notes #2/#3/#4 and the multi-condition rule ("if all of the Sale Conditions indicate that the trade qualifies it is included; if any one of them is NO the trade does not qualify"; a condition with Note #2/#3/#4 governs). Applies to tapes A and B.
- **UTP Data Feed Services Specification v4.1, Sept 2026** (`utpplan.com/DOC/UtpBinaryOutputSpec.pdf`) §3.14 "Sale Condition Matrix" ("Consolidated Update Last" column), §3.14.3 combination table, footnotes 1-3 (first/only last-sale-eligible trade of the day; End of Last Sale Eligibility 16:00:10). Applies to tape C.
Both are normative; Alpaca condition metadata is used only to translate Alpaca's provider codes into these spec codes.

Encoded tables (data module `execution/trade_conditions.py`, one table per spec, keyed `(tape family, spec code)`), value for "updates consolidated last":
- CTS (A/B): YES = space(regular), E, F, K, O, X, 5, 6, 9 (9: listing-market corrected close, post-close only). NO = B, C, H, I, M, N, Q, R, T, U, V, 7, 8. CONDITIONAL-FIRST-ONLY (Notes #2 "only qualifying last") = P, Z, 4. CONDITIONAL (Note #3) = L: "only qualifying last, or same participant as the last, or listing market".
- UTP (C): YES = @, A, B, D, F, K, L (only before 16:00:10, so always true in the open+30 window), O, S, X, Y, 1, 5, 6, 9. NO = C, H, I, M, N, Q, R, T, U, V, W, 7. CONDITIONAL-FIRST-ONLY (footnote 1) = G, P, Z, 4. TBD in spec = E, 8 (treated as unknown, fail closed).
- Combination (all specs): every condition on the trade must qualify. Any NO => ineligible. Any unknown / TBD / unmapped code, or unknown tape => UNKNOWN. UNKNOWN on the candidate makes the reference unresolved (never skips to an earlier trade). Ambiguity fails closed.
- Conditional codes are evaluated against the same-day trade sequence fetched from 00:00 ET (must be complete: incomplete pagination => unresolved): "first/only qualifying" is true iff no earlier fully-qualifying trade exists that day. CTS Note #3 (L) needs participant / listing-market facts we do not have, so L is eligible only when it is the only qualifying last, otherwise the result is unresolved (fail closed, not skipped).
- Provider-code layer (`ProviderCodeMap`), **fail-closed in production**: Alpaca returns `@` for regular sale on every tape, while CTS uses a space. A checked-in mapping file `config/trade_condition_map.yaml` lists per `(tape, alpaca_code)`: Alpaca's name, the spec code and spec name, and `validated: bool`. Every entry ships `validated: false`, because no real live mapping has been verified here. The production resolver (any non-test mode: backtest references, halt reconstruction) accepts only `validated: true` entries; a trade carrying any other code makes the reference unresolved with reason `provider_mapping_unvalidated`. A synthetic recorded `/v2/stocks/meta/conditions/trade?tape=A|B|C` fixture is enough for offline gate tests only, through an explicit test-only mapping object; it never sets `validated`. The credentialed smoke probe fetches the live metadata for all three tapes, checks **every returned tape/code/name** against the spec names, fails on drift, on any unmapped/unknown code, or on any mismatch, and only emits a proposed mapping file for the owner to review and commit (the code never flips `validated` itself). Reported as a blocker/limitation: live use needs that probe run once with keys.
- Regular-session window: trade time in `[open_at, ref_time]` from the stored calendar session (so an early close/late open moves the window); anything else ineligible.

## Schema (migration `0007_p6_market_data`, down_revision `0006`)
All new fact tables append-only, versioned by the repo's existing rule (max `(available_at, source_version)` at `available_at <= as_of`) unless noted.
- `securities`: as above.
- `trading_calendar(session_date, open_at, close_at, available_at, ingested_at, source_version)`; unique `(session_date, source_version)`. A revised session is a new row (`source_version` = `alpaca_calendar:<sha8 of the raw row>`); nothing is updated or deleted. Insert-only trigger. `available_at` = the fetch time (true knowledge time), so a later revision never alters an earlier `as_of` read.
- `calendar_coverage(source, range_start, range_end, available_at, ingested_at, source_version, session_count, sessions_sha256)`, insert-only, written in the **same transaction** and with the same `available_at` as the sessions it covers, only after a fully successful, error-free fetch of that range. Semantics: a date inside a range confirmed at `available_at <= as_of` with no session row is a closed day; a date in no confirmed range is unresolved. Never inferred from weekdays or `max(session_date)`. **One point-in-time view**: the reader takes a single `as_of`, selects per range the latest coverage row with `available_at <= as_of`, loads the sessions visible at that same `as_of` (version rule) and verifies that their hash equals that coverage row's `sessions_sha256`; a mismatch raises `CalendarCoverageError` (fail closed). A later session revision arrives with a **new** coverage row (new hash, later `available_at`), so a coverage row can never make a newer revision visible to an older `as_of`.
- `tbill_rates(series, observation_date, yield_pct, vintage_date DATE, ingested_at, source_version)`. **No fabricated timestamp and no `available_at` column.** `vintage_date` (ALFRED `realtime_start`) is authoritative historical-knowledge evidence and stays separate from `ingested_at` (when we fetched it). `vintage_end`/`realtime_end` is not stored (it changes as later vintages appear; the next vintage is its own row). Unique `(series, observation_date, vintage_date)`, insert-only trigger. FRED "." (missing) values are not stored. **Explicit, documented exception** to the repo-wide `available_at` invariant: `TBillObservation` is a plain `Contract`, not a `Fact`, and blueprint §4.3 line 220 ("every fact table carries event_time, available_at, ingested_at, source_version") gets a named exception for `tbill_rates` with the reason. Historical eligibility is **date-granular**: for accrual session date `P`, only `vintage_date < P` is usable; a same-day vintage is never usable (no authoritative release time is stored). "Prior session" and the observation-date search use the **stored trading calendar** (`previous_session(P)`, coverage required, else unresolved), never business-day arithmetic. This is stated in the spec (§4.3, §12.3), the `TBillObservation` docstring and `evaluation/tbill_rules.py`.
- `tbill_vintage_coverage(series, earliest_vintage, latest_vintage, vintage_count, vintage_dates_sha256, established_at, source_version)`, insert-only: one row per establishment run derived from the fetched ALFRED `vintagedates` list; the reader takes the latest row with `established_at <= as_of`.
- `execution_references(run_id, symbol_ref, ref_time, mode[live|backtest], status[resolved|unresolved], reason, price NULL, source NULL, trade_time NULL, trade_tape NULL, trade_conditions NULL, trade_id NULL, session_date, available_at, ingested_at, source_version)`. **Stays run-scoped, key `(run_id, symbol_ref)`**, exactly as blueprint l.212; no `reference_set_id`, no blueprint change to the key. Each row carries its full evidence inline, so two trials on the same date keep distinct, independently traceable provenance (each has its own `run_id`; duplicated SIP fetches across trials are accepted for auditability, and a per-process cache may avoid refetching). Insert-only trigger. Only additive spec edit: add `status/reason` and the evidence columns to the §4.3 line, and add `calendar_coverage` and `tbill_vintage_coverage`.
- `halt_reference_requests` and `halt_reference_symbol_sets`: see "Halt reference" (both insert-only, conflict-checked).
- `halt_references(run_id, trigger, symbol_ref, observed_at, lag_seconds, status, reason, price NULL, source NULL, trade_*, symbol_set_source, symbol_set_version, available_at, ingested_at, source_version)`, insert-only, key `(run_id, trigger, symbol_ref)`. `observed_at` = the actual observation time (never presented as τ-exact).
- No new `price_bars` columns: ETF/SPY bars reuse it and its raw-adjustment semantics.
- Reversible down migration (drop triggers, tables, index, check, restore `cik NOT NULL` only if no ETF rows). Update `tests/conftest.py` truncation list, `test_every_section_4_3_table_exists`, `FACT_TABLES`/`IMMUTABLE_TABLES` (all new tables are plain tables, no hypertable), and the metadata drift test.

## Pure logic (no I/O)
- `execution/trade_conditions.py`: the normative tables above, `ProviderCodeMap`, `evaluate_trade(tape, codes, prior_trades) -> ConditionEligibility`.
- `execution/reference_rules.py` (separates price resolution from scheduling, per point 7):
  - `resolve_live(source, symbol, at) -> ReferenceObservation`: the shared §9 resolver for any timestamp `at`. It calls the existing `reference_price(source, symbol, at)` unchanged (IEX mid if spread <= 50 bps, otherwise SIP trade at least 15 minutes old) and maps `NoReferencePriceError` to an `unresolved` observation. It knows nothing about Mondays, opens or sessions. Execution calls it with D0 open+30; halt capture calls it with the actual trigger time `τ`.
  - `resolve_backtest(trades, session, ref_time)`: latest trade in `[open_at, ref_time]`; UNKNOWN on the candidate => unresolved; ineligible => continue to an earlier trade; none => unresolved. Never a daily bar.
  - `reconstruct_halt(trades, tau, sessions)`: first eligible trade at/after `τ` within one session (§9 fallback), else unresolved. Not used to compute returns.
- `evaluation/calendar_rules.py` (pure, added to the purity contract): `TradingCalendar` built from stored sessions + confirmed coverage ranges. `session_status(date)` = OPEN | CLOSED | UNCOVERED; `d0(friday_as_of)` = next stored session strictly after the as_of session (can be Tuesday after a holiday); `horizon_session(d0, h)` for 5/21/63 counts stored sessions only and raises `CalendarCoverageError` when any date it must cross is UNCOVERED or when the horizon runs past the confirmed coverage. No weekday arithmetic anywhere.
- `evaluation/tbill_rules.py` (pure): `select_rate(rows, coverage, period_start)`: for the accrual day `P`, only vintages with `vintage_date < P` are usable (a rate must be known at the start of the day; a same-day vintage is never usable because no authoritative release time is stored). Per observation take the latest usable vintage; the rate used is the observation for the latest observation date `<= TradingCalendar.previous_session(P)` that has a usable vintage (no business-day arithmetic anywhere, only stored sessions inside confirmed coverage). Returns `Unresolved(reason)` when `P` is before the earliest usable vintage, no usable vintage exists, or coverage is missing. There is no observation-date+1-day rule and no synthetic availability.

## Halt reference: durable request + async resolution (revised; no threads)
No thread of any kind is started from `HaltController`. Market data is never touched on the halt path.
- Two insert-only tables (final schema, below): `halt_reference_requests` (pending request, never holds symbols) and `halt_reference_symbol_sets` (the reconstructed set, written only by the sweeper).
- **P5 halt semantics are preserved, not reordered.** The existing sequence stays exactly as it is (`ks.halt`, cancel/confirm, flatten only for manual, then the event record in the existing `finally`). The only change on the halt path is that the existing halt write (`DecisionSink.record_halt` -> `write.record_halt`, which already inserts the `kill_switch_events` row and moves the run to `PARTIAL` in one transaction) also inserts the `halt_reference_requests` row **in that same transaction**, so the durable request exists iff the halt event and state transition exist. The new invariants: no market-data lookup, Celery dispatch or symbol discovery occurs synchronously on the halt path; kill-switch event + `PARTIAL` transition + pending request are persisted in the same existing transaction, and a rollback leaves none of the three. If the current `record_halt` signature/`HaltController.record_event` structure needs a small change to carry the request, make only that change and re-run the P5 halt and e2e tests (`tests/execution/test_halt.py`, `tests/orchestration/test_execution_stage.py`, `test_store_execution.py`, `test_p5_e2e.py`).
- **No dispatch and no symbol discovery on the halt path.** The halt path ends after the existing halt transaction, which now also inserts the `halt_reference_requests` row. `HaltController` performs zero Celery/broker calls, zero market-data calls and zero intended-symbol discovery. No immediate wake-up is implemented (it is not needed for correctness; omitted rather than risk a blocking call). The beat sweeper `orchestration.sweep_halt_references` (every 5 minutes) is the only discovery/dispatch mechanism: it finds requests without a complete set of reference rows and processes them, so halt completion never depends on Celery, the broker or the network.
- **Final schema, request:** `halt_reference_requests(run_id, trigger, tau, status, requested_at, source_version)`; `status` is a CHECK-constrained column that can only be `'symbols_pending'`; key `(run_id, trigger)`. Nothing else: the run id already links to the committed book and universe snapshot, and `tau` is the trigger time. There is no `intended_symbols` column (not even nullable), so an empty set can never be stored as a successful discovery. State (pending / set resolved / references complete) is derived from the presence of rows in the later tables; the request row is never updated.
- **Final schema, symbol set:** `halt_reference_symbol_sets(run_id, trigger, symbols JSONB, symbol_count, symbols_sha256, source, source_version, resolved_at)`, key `(run_id, trigger)`, insert-only. **One canonical definition** in pure `execution/halt_symbols.py::reconstruct_symbol_set(book_symbols, universe_symbols, reference_instruments)`: the union of (symbols in the durable committed book/positions for the run) + (symbols of the universe snapshot in effect at the run's as_of) + (the configured reference instruments: SPY and the 11 sector ETFs from `config/sectors.yaml`), each upper-cased, deduplicated and sorted lexicographically; `symbols_sha256` = SHA-256 of the `\n`-joined sorted list; `source` = `committed_book+universe_snapshot+reference_instruments`, `source_version` = `halt_symbols_v1` plus the ids/dates of the snapshot and config hash used, which together with the hash reproduce the exact set. An **empty or failed reconstruction is not success**: nothing is written, the request stays pending, and the failure (reason, run id) is emitted to logs/telemetry; the immutable request is never mutated. The sweeper alone reconstructs symbols and resolves references. Each `halt_references` row records `symbol_set_source`/`symbol_set_version` and the set hash.
- The sweeper (which runs `capture_halt_references` per pending request inside the task; a lost worker never loses evidence because the request is durable) resolves each request idempotently: per intended symbol, first the shared resolver `resolve_live(source, symbol, at)` when the task runs within a short grace of τ (the resolved `observed_at` is the actual observation time and the row records `lag_seconds = observed_at - τ`, so it is never presented as a τ-exact price); otherwise, once τ + SIP delay has passed, `reconstruct_halt` (first eligible SIP trade at/after τ within one session, §4.6 eligibility). Before the deterministic deadline (end of the first regular session at/after τ, plus the SIP delay) an unresolvable symbol is **deferred** (no row). After the deadline it gets a durable `unresolved` row per symbol with a reason (`no_eligible_trade`, `sip_entitlement`, `provider_mapping_unvalidated`, `incomplete_trades`, `calendar_uncovered`). Rows go through `DecisionSink.record_halt_references` (insert-only, conflict-checked). Redelivery is a no-op; a contradictory redelivery fails loudly.
- No adjusted return is computed and the halt-day close is never used.

## Scheduling (point 6, 10)
- No Monday/10:00 cron. `orchestration.capture_due_references` is a polling beat task (every 5 minutes). It reads the stored calendar; for each LIVE run in an eligible status with no reference rows, it computes D0 = next stored session after the run's as_of session (Tuesday after a Monday holiday; early or changed sessions move the open) and, once `now >= D0 open + 30 min` and before D0 close, calls the shared resolver at D0 open+30 for every required symbol (held + SPY + 11 ETFs + universe names in the run's book) and writes insert-only rows through the sink. Idempotent by the `(run_id, symbol_ref)` key.
- **Deferral before failure**: missing calendar coverage, or a not-yet-due window, writes nothing and returns `deferred`; a temporary ingestion lag is never turned into an immutable failure. The wait is bounded by a **named, configured** value `reference_data.calendar_coverage_wait_minutes` (validated > 0, in `pipeline.yaml` + `ReferenceDataConfig`), measured from exactly one durable, immutable timestamp: `committed_at` of the run's `decision_commitments` row (insert-only, recorded once by the sink, the same instant on every replay), so the deadline `committed_at + calendar_coverage_wait_minutes` (used **only** to decide when unresolved `calendar_uncovered` evidence may finally be persisted, and never to determine, approximate or bound D0, a session date or open/closed status) is deterministic across retries and redeliveries and a replay can never move it. The task's `now` is compared against that fixed deadline; nothing else defines it. It is an operational timeout only: it never infers D0, session status or a session date. Until it expires, uncovered calendar state is `deferred`; after it expires, unresolved rows with reason `calendar_uncovered` are persisted per symbol. Symbols still unresolvable once the window is due (no eligible trade, entitlement, unvalidated mapping) get `unresolved` rows with reasons. Tests cover before-timeout deferral, after-timeout terminalization, and that coverage arriving before the timeout leads to a normal capture.
- Backtest references are built by `build_backtest_references(run_id, ...)`, called for a BACKTEST/ABLATION run once its as_of is known; it uses the stored calendar to find D0 open+30 and the SIP resolver.
- `orchestration.sync_calendar` (daily; fetches a forward window covering at least 63 sessions plus history on demand) and `orchestration.sync_dgs3mo` (daily), `orchestration.ingest_benchmarks` (daily, existing bar path for ETF instruments).
- New config block `pipeline.yaml` `reference_data.cadence_minutes` for these tasks. `freshness_sla_hours` and `ingest.cadence_minutes` are untouched; `stale_feeds` stays SLA-key driven. Optional `feed_health` rows for the new jobs use new `FeedName` members that are absent from the SLA maps; a test proves they cannot trigger a halt.
- `is_transient`: `SipEntitlementError`, `CalendarCoverageError`, `IncompleteTradesError` and unresolved outcomes are not retried; transport and 5xx errors use the existing rules. `startup.py` requires `FRED_API_KEY` only when the DGS3MO job is enabled.
- Updated: `test_tasks.py` beat name set, `test_ingest_beat.py`.

## Immutable-conflict rule (calendar, coverage, vintages, references)
Every new immutable writer uses one conflict-checking helper, `write._insert_immutable(conn, table, rows, key_cols, payload_cols)`; no new writer may call the generic `_insert`/`_insert_rows` (`ON CONFLICT DO NOTHING`) for calendar, coverage, Treasury vintages, execution/halt references, halt-reference requests or symbol sets (a test scans `store/write.py` to enforce this). The helper inserts with `ON CONFLICT DO NOTHING RETURNING`, and for each row that did not insert, reads the stored row by its natural key and compares `payload_cols` (excludes `ingested_at` only) after **canonicalizing both sides** through one function `_canonical(value)`: `Decimal`/`float` compared numerically at the column's declared precision, `datetime` normalized to UTC-aware (naive rejected), `date` as ISO, enums as `.value`, JSON/JSONB with sorted keys, arrays as ordered lists (order is significant only where the payload defines it), `None` distinct from empty. Exact semantic replay therefore never false-conflicts, and a genuinely different payload always raises. Tests round-trip each column type through Postgres and compare, plus negative cases per table. (Benchmark ETF bars keep using the existing `insert_price_bars` path unchanged; that is not a new writer.) Identical replay is accepted; a differing price/source/status/evidence/`yield_pct`/session times/hash under the same key raises `ImmutableConflictError` (loud, not retried by the tasks). Applies to `trading_calendar`, `calendar_coverage`, `tbill_rates`, `tbill_vintage_coverage`, `execution_references`, `halt_references`, `halt_reference_requests` and `halt_reference_symbol_sets`. Calendar sessions and their coverage row are written by one function, `write.insert_calendar_range(conn, sessions, coverage)`, in a single transaction; `sessions_sha256` is computed by one function `calendar_hash(sessions)` over a **canonical serialization**: sessions sorted by `session_date`, each rendered as `session_date|open_at(UTC ISO, microseconds)|close_at(UTC ISO)|source_version` joined by `\n` (all fields whose revision matters; independent of row, dict or JSON ordering), SHA-256 hex. Golden tests pin a fixed session list to a fixed digest and prove: input-order invariance; timezone-normalized canonical representation (the same instants given in ET and UTC hash identically); sensitivity to each of `session_date`, `open_at`, `close_at` and `source_version`; exact semantic replay after a DB round-trip (no false conflict); and that contradictory immutable payloads under one natural key fail loudly with `ImmutableConflictError`. The hash covers exactly the sessions in the range, so a revised session set necessarily produces a new coverage record/hash in that same transaction, and readers validate the hash against exactly the session versions visible at the same `as_of`. Tests: identical replay is a no-op; contradictory replay raises for each table.
