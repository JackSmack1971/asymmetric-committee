## Scope

- Persist 5/21/63-session outcomes against each run's immutable execution references. Compute security and sector ETF returns from confirmed stored trading sessions, raw bars, and prospective P6.4 evidence only.
- Admit the run before any outcome-bearing read. The scoring ticket's `requested_at` is the evidence cutoff for all loaders and writers. BACKFILL/sensitivity readers are excluded.
- A no-action conclusion requires a stored complete, all-type, fully paginated Alpaca snapshot whose proven provider scope covers every process date that could contribute by `requested_at`. Alpaca filters on `process_date` and promises no creation-time bound, so no ex-date-to-process-date mapping is allowed. Its current endpoint supports `capital_gains_distribution`; add that type as stored `UNINTERPRETED` evidence so the provider's all-type response is not silently truncated. Full-history requests omit the `types` filter, persist the actual date scope and pagination exhaustion, and are eligible only if the provider-supported lower bound/scope is established. Omitted `start`/`end` are not full-history evidence because their documented default is the current day. If the required range cannot be proven, leave the horizon unresolved. Refresh rows are first-observed and never backdated; the refresh must precede ticket admission to be eligible at `requested_at`.
- `outcomes` logical identity is `(run_id, security_id, horizon)`, with a deterministic evidence/payload revision hash and monotonic durable `revision_id` for selection when authoritative `resolved_at` timestamps tie. Exact replay is idempotent; changed later evidence appends a revision. `resolved_outcomes(as_of)` picks the latest eligible revision ordered by `(resolved_at, revision_id)` with `resolved_at <= as_of`; no prior row is mutated.
- `resolved_at` is the maximum authoritative knowledge time of every dependency used. `UNRESOLVED` is no valid revision; `MISSING` remains a run/evaluation-period classification and never becomes a zero-valued outcome.
- COMPLETE runs compute 5/21/63 together. The initial outcome write and `ANCHORED`/`EXECUTED` → `SCORED` transition are one transaction and happen only when all three latest outcomes are COMPLETE. Otherwise write no initial COMPLETE outcome rows and leave the run in its prior complete status.
- HALTED runs persist each independently resolved horizon as `HALTED`; unresolved horizons stay absent, and the run remains `PARTIAL` forever. No scorer, retry, trigger, or generic transition may promote it to `SCORED`.
- Delisting handling uses explicit terminal effective date, otherwise supported P6.4 last-trade/effective evidence. Cash, worthless, and default terminal values stay flat thereafter. Stock/mixed consideration carries acquirer shares plus cash to the original horizon under the same calendar/raw-bar/action rules; incomplete acquirer evidence is unresolved, never replaced with the −30% default.
- Return formula: `r = (P_exit*F + Σ cash_d*F_d)/P0 - 1`; include actions only for `entry_day < ex_date <= exit_day`, hold dividends as cash, apply splits locally, and derive 5/21/63 horizons only from confirmed stored calendar coverage.

## Spec issues

The [official Alpaca Corporate Actions API reference](https://docs.alpaca.markets/us/reference/corporateactions-1) includes `capital_gains_distribution` and documents `start`/`end` defaults as the current day. The blueprint and this plan now require that known type to be retained as uninterpreted, require explicit proven range/scope for full-history coverage, and prohibit treating an omitted date range as all history. No provider-supported historical lower bound is established by the checked reference; until a provider response/contract establishes it, no-action horizons remain `UNRESOLVED`. This design does not invent an ex-date-to-process-date mapping or backdate refreshed evidence.
