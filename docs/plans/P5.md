## Architecture

`BacktestOrchestrator` (`orchestration/pipeline.py`) is the one engine for backtest and single-period live runs. Celery (`orchestration/tasks.py`) wraps its stage methods; it never re-implements stage logic. Execution (`execution/`, `risk/kill_switch.py`) and anchoring sit after `COMMITTED`, per the §13 state machine:
`PENDING → INGEST_OK → FEATURES_OK → AGENTS_OK → COMMITTED → ANCHORED → EXECUTED → SCORED` (+ `FAILED`, `PARTIAL`).
Backtest mode stops at `ANCHORED` (anchored, never executed; scoring is P6). Live mode runs the full chain; execution needs an `ANCHORED` run with a recomputed, matching commitment. Only paper endpoints exist (CLAUDE.md).

### Step 5 — Anchoring, state machine, Celery (as built; supersedes the draft)
Owner decisions applied (2026-09-26): halt after `EXECUTED` -> `PARTIAL` via the audited halt path; halt recovery = fresh `run_id`; a maintained OpenTimestamps library (`opentimestamps` 0.4.5, LGPL, Python 3.12 verified); execution does **not** wait for Bitcoin; Alpaca's official calendar (`GET /v2/calendar`) is the scheduling authority; `commitment_v1` approved; `RunStatus.GATED` untouched; the git anchor remote/branch are owner configuration; no commits or pushes were made.
- **State machine.** `RunStatus.ANCHORED` added (`COMMITTED -> ANCHORED -> EXECUTED`; `ANCHORED -> SCORED` for non-live). Committedness is defined by the `decision_commitments` row, never by `runs.status`. A kill-switch halt moves `COMMITTED|ANCHORED|EXECUTED -> PARTIAL` in the same transaction as its `kill_switch_events` row (`write.record_halt`); that `PARTIAL` is terminal and nothing overwrites it. Commitment, anchor, order and halt rows are never cleared.
- **Commitment.** `contracts/commitment.py` is the only hash definition (`commitment_v1`: run identity, decisions sorted by security and horizon, snapshot incl. CIO; UTC datetimes, sorted compact JSON). It is recomputed from stored rows (`load_commitment_material`, one REPEATABLE READ snapshot) before anchoring, before every execution, and by `inspect-run`. Mismatch = `CommitmentIntegrityError`: zero broker calls, no anchor, a DLQ row, never retried. Migration 0006: `committee_decisions.entity_token` (needed to rebuild the hashed rows), composite FK `commitment_anchors(run_id, sha256) -> decision_commitments`, append-only `run_resets`.
- **Anchoring** (`evaluation/anchoring.py` pure; `orchestration/anchor_adapters.py`, `anchor_stage.py`). `ANCHORED` needs: recomputed hash matches; an OTS proof from >= `ANCHOR_OTS_MIN_CALENDARS` calendars that binds the exact digest; a manifest `anchors/<run_id>.json` pushed to the configured git remote and confirmed reachable; then anchor row + status move in one transaction. Bitcoin confirmation (`AnchorUpgrader`, header check against a block-header source) is required before scoring, not before execution.
- **Celery** (`orchestration/tasks.py`, `celery_app.py`). Business truth is Postgres + the broker; Redis is transport/cache/limiter only. Stage-level tasks (`run_weekly_pipeline`, `advance_run`, `execute_run`, `reconcile_orders`, `upgrade_anchors`, `sweep_runs`), acked late, Postgres advisory locks per `(stage, run_id)`, `claim_run` for one run per `(mode, as_of, config)`, retries only for transient infrastructure errors, `sweep_runs` rebuilds the queue from Postgres. Execution only inside the first session after the close, open + 30 min .. close; a stale plan is never traded.
- **Reset.** `POST /runs/{id}/reset` (bearer token, 503 when unset) clears only a run with no commitment/anchor/order/halt event and no worker holding it; the cleared rows go to `run_resets`.
